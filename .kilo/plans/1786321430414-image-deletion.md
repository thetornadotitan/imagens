# Image Deletion Plan

## Goal
Allow users and admins to delete generated images with full cleanup (database + filesystem).

## Scope

### In Scope
- Backend DELETE endpoint for individual images
- Database layer function to delete a generation record
- Filesystem cleanup (remove the PNG file from disk)
- User-facing delete button in "My Works" image grid overlay
- Admin delete button in admin generation logs
- Confirmation dialog before delete
- i18n strings (en/zh)
- Error handling (missing file, not found, permissions)

### Out of Scope
- Batch/bulk delete
- Soft delete / undo
- Delete from the image viewer modal
- Delete from the public gallery view

## Design Decisions

### 1. Route: `DELETE /api/images/<id>`
Reuse the existing `<id>/file` route pattern by handling DELETE method on `^/api/images/([^/]+)/file$`. The method distinguishes GET (serve file) from DELETE (remove image).

- **Auth**: Requires authentication (`ensureAuthenticated`)
- **Authorization**: Uses existing `canTouchGeneration(user, generation)` — owner or admin
- **If not found**: 404
- **If owner/admin**: Delete DB row + filesystem file
- **If file missing on disk**: Delete DB row anyway, proceed gracefully
- **Response**: 200 with `success: true`

### 2. DB Layer: `mysql-store.js`
Add `deleteGeneration(id)` function following the pattern of `deleteUser()` — a simple single-statement DELETE.

### 3. Filesystem Cleanup
Extract `user_id` and `filename` from the stored path, build absolute path using `GENERATED_DIR`, and call `fs.unlink()`. Use the same pattern as `cleanOldLogs()`.

### 4. UX
- **User "My Works"**: Add a delete button (🗑 icon, `ri-delete-bin-line`) to the existing `.cell-overlay` buttons alongside download, regenerate, edit prompt, and edit image
- **Admin Log**: Add a delete button per row in the generation logs table
- **Confirmation**: `confirm()` dialog before delete
- **On success**: Remove from client-side state + re-render (no full page reload needed)
- **On failure**: Show error toast
- **Empty state**: If last image deleted, user sees the "No generated images yet" message naturally

### 5. i18n
Add `"delete"` key to both `zh` and `en` i18n objects.

## Validation

1. **User deletion**: Login as regular user, go to "My Works", click delete on own image, confirm → image removed from grid, file deleted from disk, DB row gone
2. **Admin deletion**: Login as admin, go to admin logs, click delete on any image → same cleanup
3. **Permissions**: User tries to delete another user's image via admin filter → 404
4. **Missing file**: Delete generation where file no longer exists on disk → DB row removed, success toast
5. **Not found**: Delete with invalid ID → 404 response
6. **Unauthenticated**: Delete without login → 401 response
7. **i18n**: Switch to Chinese UI, delete button shows Chinese label
8. **State sync**: After deletion, grid re-renders, item count decrements

## Risks / Edge Cases

- **File on disk missing**: Handled — DB row deleted, file delete error swallowed
- **Race condition (two tabs)**: Second delete gets 404 — benign
- **Large filesystem**: Individual `fs.unlink()` is synchronous enough for single file
- **Docker volume**: Files are on mounted volume — `GENERATED_DIR` path is `/app/data/generated` inside container — matches `path.join(GENERATED_DIR, generation.filename)`
